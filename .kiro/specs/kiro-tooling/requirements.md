# Requirements Document

## Introduction

The kiro-tooling feature adds three Kiro-native developer tools around the character dataset, so judges can see Kiro features doing real work: an agent hook that rebuilds and re-tests the dataset whenever its inputs are saved, a read-only custom agent that checks the repository text against `content-accuracy.md`, and the Cangjie Oracle, an MCP server that answers verified character-data questions from the committed dataset. A later task packages the Oracle as a Kiro Power. No game behaviour changes and the shipped web app is untouched.

The feature stays small (about one day of work). Tests are Vitest unit tests only. No property-based tests are added, following the decision recorded in `tech.md` (Nov 15). Character data is never generated by a model: the Oracle returns only values that already exist in `app/public/data/characters.json`.

### Kiro features used

| Part | Kiro feature | Where it lives |
| --- | --- | --- |

## Glossary

- **Data_Check_Hook**: The agent hook defined in `.kiro/hooks/data-check-on-save.json`.
- **Watched_Inputs**: The files `data/character-list.txt` and `data/prompt-overrides.csv`, and every file under `data/raw/`.
- **Data_Check_Command**: The script `scripts/data-check.ts`, started with `npm run check:data`, which runs the Dataset_Build and then the Dataset_Tests.
- **Dataset_Build**: The command `npm run build:data`, which runs `scripts/build-data.ts`.
- **Build_Script**: The module `scripts/build-data.ts`, including its `buildDataset` function and its command-line entry point.
- **Dataset_Tests**: The Vitest `node` project (`tests/**/*.test.ts`), started with `npm run test:data`.
- **Override_File**: `data/prompt-overrides.csv`, whose rows give `character,entryIndex,meaningIndex,reviewedBy`.
- **Override_Index_Error**: A build failure in which an override names an `entryIndex` or `meaningIndex` outside the character's CC-CEDICT data, or names a character that is not in `data/character-list.txt`.
- **Accuracy_Reviewer**: The custom agent defined in `.kiro/agents/accuracy-reviewer.json`.
- **Review_Scope**: The app text (strings in `app/src/**` and `app/index.html`), the spec documents in `.kiro/specs/**`, and `README.md`.
- **Accuracy_Rules**: The rules in `.kiro/steering/content-accuracy.md`.
- **History_Claims**: The four Cangjie history claims allowed by the Accuracy_Rules: developed in the 1970s by Chu Bong-Foo; named after Cangjie, the legendary inventor of Chinese writing; the first Chinese input method to use the standard QWERTY keyboard; released to the public in 1982.
- **Answer_Leak**: A place where the hidden character of a ghost is shown to the player as text, an attribute or a label before the player has written it.
- **Cangjie_Oracle**: The MCP server in `oracle/`, named `cangjie-oracle`.
- **Dataset_File**: The committed file `app/public/data/characters.json`.
- **Oracle_Tools**: The three tools `lookup`, `verify` and `decompose` exposed by the Cangjie_Oracle.
- **Cangjie_Source**: The object `{ dataset: "unihan", version: "18.0.0", field: "kCangjie", provisional: true }` that names where a Cangjie code comes from.
- **Valid_Character_Input**: A string of exactly one Unicode code point in the CJK Unified Ideographs block U+4E00 to U+9FFF.
- **Normalised_Code**: A code argument after conversion to upper case, before validation.
- **Valid_Code_Input**: A code argument whose Normalised_Code is accepted by `isValidCangjieCode` (one to five letters A to Y, pattern `^[A-Y]{1,5}$`).
- **Manual_Check_Command**: The command `npm run check:data`, run by a person in a terminal.
- **Workspace_MCP_Config**: The file `.kiro/settings/mcp.json`.
- **Oracle_Power**: The Kiro Power package in `oracle/power/` that bundles the Cangjie_Oracle.
- **Unit_Test_Suite**: The Vitest tests added by this feature.

## Requirements

### Requirement 1: Data check hook

**User Story:** As a maintainer, I want the dataset rebuilt and tested whenever its inputs are saved, so that a bad edit is caught in the Kiro chat at once.

#### Acceptance Criteria

1. WHEN a file in the Watched_Inputs is saved, THE Data_Check_Hook SHALL run the Data_Check_Command.
2. THE Data_Check_Hook SHALL use a `PostFileSave` trigger with a command action and a matcher that selects the Watched_Inputs and no other path, so that `app/public/data/characters.json` and `data/prompt-review.csv`, which the Dataset_Build writes, do not trigger the hook again.
3. THE Data_Check_Hook SHALL set a timeout of 300 seconds.
4. WHEN the Data_Check_Command runs, THE Data_Check_Command SHALL run the Dataset_Build first and the Dataset_Tests second.
5. IF the Dataset_Build fails, THEN THE Data_Check_Command SHALL skip the Dataset_Tests.
6. WHEN both steps succeed, THE Data_Check_Command SHALL exit with code 0 and print a first line starting with `DATA CHECK PASSED`.
7. IF a step fails or cannot start, THEN THE Data_Check_Command SHALL exit with code 1 and write to standard error a first line starting with `DATA CHECK FAILED`, the name of the failing step, and the last 40 lines of that step's combined output.
8. WHEN the agent saves a file in the Watched_Inputs, THE Data_Check_Hook SHALL fire; saves made by a person in the editor are not required to fire it (decision approved by Takshil).

### Requirement 2: Override index failures are visible

**User Story:** As a maintainer, I want a bad override index to fail the build with a clear message, so that a wrong ghost prompt never reaches the dataset.

#### Acceptance Criteria

1. IF an override has an `entryIndex` that is negative or not smaller than the number of CC-CEDICT entries of its character, THEN THE Build_Script SHALL return a failed result with the override error `entry-index-out-of-range` for that character and no output.
2. IF an override has a `meaningIndex` that is negative or not smaller than the number of meanings of the chosen entry, THEN THE Build_Script SHALL return a failed result with the override error `meaning-index-out-of-range` for that character and no output.
3. IF an override names a character that is not in `data/character-list.txt`, THEN THE Build_Script SHALL return a failed result with the override error `unknown-character` for that character and no output.
4. WHEN THE Build_Script reports an Override_Index_Error on the command line, THE Build_Script SHALL print the character, the reason in plain words, the file `data/prompt-overrides.csv` and the column to correct, and SHALL exit with code 1.
5. IF an Override_Index_Error occurs, THEN THE Build_Script SHALL leave `app/public/data/characters.json` and `data/prompt-review.csv` unchanged.

### Requirement 3: Accuracy reviewer agent

**User Story:** As a maintainer, I want a read-only agent that checks our text against the accuracy rules, so that unsourced claims and answer leaks are found without any risk to the files.

#### Acceptance Criteria

1. THE Accuracy_Reviewer SHALL be a custom agent defined in `.kiro/agents/accuracy-reviewer.json`.
2. THE Accuracy_Reviewer SHALL list only the `read` tool category in its `tools` field.
3. THE Accuracy_Reviewer SHALL carry permission rules with effect `deny` for the capabilities `fs_write` and `shell`.
4. THE Accuracy_Reviewer SHALL load `.kiro/steering/content-accuracy.md` as a resource.
5. WHEN the Accuracy_Reviewer is asked to review, THE Accuracy_Reviewer SHALL check the Review_Scope against five rules: every claim is sourced; only the History_Claims appear; the words "dead" and "dying" are not applied to Cangjie; every licence required by the Accuracy_Rules is listed in the README; no Answer_Leak exists.
6. WHEN the Accuracy_Reviewer finds a violation, THE Accuracy_Reviewer SHALL report the file path, the line number, the rule violated and the quoted text.
7. WHEN the Accuracy_Reviewer finds no violation, THE Accuracy_Reviewer SHALL report `No findings` and list the files it checked.
8. THE Accuracy_Reviewer SHALL quote the text of a finding without proposing replacement character data.

### Requirement 4: Oracle tools

**User Story:** As a maintainer using Kiro, I want to ask for a character's Cangjie code, check a code and see a decomposition, so that I can verify data without reading the dataset by hand.

#### Acceptance Criteria

1. THE Cangjie_Oracle SHALL be a Node and TypeScript MCP server named `cangjie-oracle` that uses `@modelcontextprotocol/sdk` over a stdio transport.
2. THE Cangjie_Oracle SHALL expose exactly the Oracle_Tools `lookup`, `verify` and `decompose`.
3. WHEN `lookup` receives a Valid_Character_Input present in the Dataset_File with a non-null code, THE Cangjie_Oracle SHALL return the character, the code, the Cangjie_Source and a `playable` flag computed by `isPlayableInCangjie`.
4. WHEN `lookup` receives a Valid_Character_Input present in the Dataset_File with a null code, THE Cangjie_Oracle SHALL return the code `null`, the source `null` and `playable` false.
5. WHEN `verify` receives a Valid_Character_Input present in the Dataset_File and a Valid_Code_Input, THE Cangjie_Oracle SHALL return the Normalised_Code in a `normalisedCode` field, `matches` true if the Normalised_Code equals the stored code and `matches` false otherwise, together with the Cangjie_Source.
6. WHEN `verify` receives a character whose stored code is null, THE Cangjie_Oracle SHALL return `matches` false and the reason `no-code-in-source`.
7. WHEN `decompose` receives a Valid_Character_Input present in the Dataset_File, THE Cangjie_Oracle SHALL return the IDS decomposition string, the `atomic` flag, the radical and the component list exactly as stored, with the source `make-me-a-hanzi`.
8. THE Cangjie_Oracle SHALL import `isPlayableInCangjie` and `isValidCangjieCode` from `app/src/engine/cangjieRules.ts` and the record types from `app/src/data/types.ts`, and SHALL NOT restate their rules.

### Requirement 5: Verified answers only

**User Story:** As a maintainer, I want the Oracle never to guess, so that its answers can be trusted as much as the dataset.

#### Acceptance Criteria

1. THE Cangjie_Oracle SHALL return only values stored in the Dataset_File, the Cangjie_Source constants and the fixed source names.
2. IF an Oracle_Tool receives a Valid_Character_Input that is not in the Dataset_File, THEN THE Cangjie_Oracle SHALL return `found` false with the reason `not-in-dataset` and no code, decomposition or components.
3. IF an Oracle_Tool receives a character argument that is not a Valid_Character_Input, THEN THE Cangjie_Oracle SHALL return an MCP tool error whose message names the argument and the rule it broke.
4. WHEN `verify` receives a code argument, THE Cangjie_Oracle SHALL convert the code to upper case before validating it.
5. IF the Normalised_Code of a `verify` code argument is not accepted by `isValidCangjieCode`, THEN THE Cangjie_Oracle SHALL return an MCP tool error whose message names the argument and the rule it broke.
6. THE Cangjie_Oracle SHALL read only the Dataset_File, SHALL open no network connection and SHALL require no API key or environment variable.
7. IF the Dataset_File is missing or is not valid JSON at start-up, THEN THE Cangjie_Oracle SHALL write a message naming the file to standard error and exit with a non-zero code.
8. THE Cangjie_Oracle SHALL write protocol messages to standard output only.

### Requirement 6: Workspace registration

**User Story:** As a maintainer, I want Kiro to start the Oracle from the workspace config, so that the tools are available in every session.

#### Acceptance Criteria

1. THE Workspace_MCP_Config SHALL define a server named `cangjie-oracle` with a `command` and `args` that start the Cangjie_Oracle over stdio.
2. THE Workspace_MCP_Config SHALL define no `env`, no `url` and no `headers` for the `cangjie-oracle` server.
3. THE Workspace_MCP_Config SHALL list `lookup`, `verify` and `decompose` in `autoApprove` for the `cangjie-oracle` server, because they only read committed data.
4. THE Workspace_MCP_Config SHALL leave `.kiro/` tracked by git.

### Requirement 7: Oracle Power (later task)

**User Story:** As a maintainer, I want the Oracle packaged as a Kiro Power, so that it can be installed and shown as a Kiro feature.

#### Acceptance Criteria

1. THE Oracle_Power SHALL contain a `plugin.json` manifest with the fields `$schema`, `name`, `version`, `description`, `author.name` and `keywords`.
2. THE Oracle_Power SHALL contain an `mcp.json` that starts the Cangjie_Oracle over stdio and defines no `env` and no `url`.
3. THE Oracle_Power SHALL contain one skill, `skills/cangjie-oracle/SKILL.md`, with `name` and `description` front matter that states when to call each Oracle_Tool.
4. THE Oracle_Power SHALL name no personal names in any file.

### Requirement 8: Documentation and Kiro log

**User Story:** As a judge or contributor, I want to know how to use each tool and how Kiro was used, so that I can run and assess them.

#### Acceptance Criteria

1. THE README SHALL contain a "Kiro tooling" section that explains how to use the Data_Check_Hook, the Accuracy_Reviewer and the Cangjie_Oracle, with the commands `npm run check:data` and `npm run oracle`.
2. THE README SHALL state that the Cangjie_Oracle reads only `app/public/data/characters.json` and returns no generated data.
3. THE `kiro-log.md` file SHALL contain one dated entry for each Kiro feature used by this feature (hooks, custom agents, MCP, steering, specs and, if built, Powers), each with the fields What I did, Kiro feature, Why and Result.
4. THE `kiro-log.md` entries written by this feature SHALL contain no personal names and no approval wording.
5. THE README SHALL state that the Data_Check_Hook is fired by agent saves, and that a person runs the Manual_Check_Command in a terminal to run the same check on demand, because the Kiro IDE offers no way to create a manual-trigger hook (decision approved by Takshil).

### Requirement 9: Tests and no regressions

**User Story:** As a maintainer, I want every new part tested and the existing checks to keep passing, so that the tooling does not break the game.

#### Acceptance Criteria

1. THE Unit_Test_Suite SHALL consist of Vitest unit tests and SHALL contain no property-based tests.
2. THE vitest workspace SHALL include an `oracle` project so that `npm test` runs the Oracle tests.
3. THE Unit_Test_Suite SHALL cover the Build_Script override failures, the Data_Check_Command, the Data_Check_Hook file, the Accuracy_Reviewer file, the Oracle_Tools and the Workspace_MCP_Config.
4. WHEN the root `npm test` runs, THE test suite SHALL pass.
5. WHEN `tsc` runs for the root, for `app/` and for `oracle/`, THE type check SHALL pass.
6. WHEN `npm run build -w app` runs, THE build SHALL succeed.
