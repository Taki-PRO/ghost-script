# Ghost Script

Ghost Script is a haunted handwriting game for people who can read Chinese characters but can no longer write them. This is known as character amnesia (提笔忘字): forgetting how to write characters you once knew, which is tied to heavy use of input methods; how widespread it is is debated ([Character amnesia](https://en.wikipedia.org/wiki/Character_amnesia), Wikipedia). It is for heritage learners and second-language learners, so the interface is in English.

**The premise:** Ghost Script is built on the premise that phonetic typing is part of why people forget how to write characters, so it brings back a shape-based way of typing as the cure. Cangjie (倉頡輸入法), developed in the 1970s by Chu Bong-Foo, builds characters from their shapes, with each basic shape assigned to a key ([Cangjie input method](https://en.wikipedia.org/wiki/Cangjie_input_method), [Chu Bong-Foo](https://en.wikipedia.org/wiki/Chu_Bong-Foo), Wikipedia). In the game, each forgotten character is a ghost: you summon it by typing its Cangjie code, shape by shape, then lay it to rest by writing it by hand. Ghosts you struggle with come back to haunt you sooner. The first time you meet a ghost, its Cangjie code is shown to copy; when it returns, the code is hidden. The summary at the end of a séance lists when each ghost returns.

Built for **Kiroween 2026**, category **Resurrection**.

## Play it

Play Ghost Script at https://taki-pro.github.io/ghost-script/. It is a static site that runs in the browser with no account. Your progress is saved only in that browser (in `localStorage`).

## Run it locally

Prerequisites: Node and npm.

1. From the repository root, install dependencies. One install covers the root and the `app` workspace:

   ```
   npm install
   ```

2. Start the dev server:

   ```
   npm run dev -w app
   ```

3. Open the localhost URL that Vite prints.

Never start the dev server with `--host`. Leaving it out keeps the server on localhost only.

Run the tests with `npm test` and make a production build with `npm run build -w app` (output in `app/dist`). See [Usage](#usage) for details.

## What the game contains

The game has 1,200 checked characters in three levels, taken from HSK 3.0 writing levels 1 to 3: level 1 has 300 characters, level 2 has 400 and level 3 has 500. Each level is its own dataset file (see [Bundle and file weights](#bundle-and-file-weights)). The player chooses a level, and the Nightly Séance draws its ghosts from the chosen level.

## Clue rule for levels 2 and 3

Level 1 prompts keep the original rule (the first usable meaning of the first CC-CEDICT entry that is not a proper noun), so `app/public/data/characters.json` and `data/prompt-review.csv` are unchanged. Levels 2 and 3 choose their default prompt like this, with no AI model:

1. **Reading.** The source is the `Examples` column of `data/raw/hsk30/hsk30-chars.csv`, which lists example words for each character. Each example word is looked up in CC-CEDICT, and every entry of the word whose syllable count matches the word counts the reading of the character's position once. The neutral tone (and any syllable without a tone digit 1 to 4) is ignored. The most frequent reading wins. If two or more readings tie, or no example word gives a reading, the reading of the original rule's entry is kept.
2. **Meaning.** The build scans the character's CC-CEDICT entries in source order, skipping proper-noun readings, and takes the first meaning of an entry with the chosen reading that contains no Chinese character and is not a cross-reference (for example "variant of", "see", "surname", "abbr.", "CL:", "(Tw)" or "(archaic)"). If no entry with that reading has such a meaning, the prompt of the original rule is used.
3. **Safety check.** The build fails, and writes no file, if a meaning shown to the player at level 2 or 3 would contain a Chinese character. The message names the character, its level and the overrides file in which a human adds a row.
4. **Human decisions win.** A row in `data/prompt-overrides-level2.csv` or `data/prompt-overrides-level3.csv` replaces the rule's prompt. A row in `data/prompt-approvals.csv` keeps the original rule's prompt, because that is the prompt the human approved.

The build writes `data/prompt-rule-changes.csv`, which lists every level 2 and level 3 prompt whose pinyin or meaning differs from the original rule's, in level 2 then level 3 list order. Its columns are `character`, `level`, `oldPinyin`, `oldMeaning`, `newPinyin` and `newMeaning`. Characters with an override or approval row are not listed. A changed prompt stays `"unreviewed"` unless an override or approval row exists, so the changes are not counted as human-reviewed. The number of changed prompts is printed by the build and is not typed in this README.

## Prompt review

A human reviews a random sample of 50 rows per level for levels 2 and 3. The build picks the sample, so the choice does not depend on anyone's taste. It writes `data/prompt-review-sample-level2.csv` and `data/prompt-review-sample-level3.csv`, each with the header of the review files and exactly 50 distinct rows copied from `data/prompt-review-level2.csv` or `data/prompt-review-level3.csv`, in the order of that review file. Open a sample file, read each row's chosen meaning and pinyin against the listed alternatives, and record the outcome in the override or approval files described under [Build the dataset](#build-the-dataset).

Sample algorithm:

1. The seed is the 32-bit FNV-1a hash of an ASCII seed string.
2. The random numbers come from the mulberry32 generator started with that seed.
3. For the `n` rows of the review file, a partial Fisher–Yates shuffle of the row positions runs for `i` from 0 to 49: the position `j` is `i + floor(random() * (n - i))`, and positions `i` and `j` swap.
4. The first 50 positions are the sample. They are sorted into the row order of the review file.

Seed strings, as recorded in `data/prompt-review-sample-provenance.json` (which also holds the numeric seeds, the sample size and the source file of each sample):

| Level | Seed string |
| --- | --- |
| 2 | `ghost-script/prompt-review-sample/v1/level2` |
| 3 | `ghost-script/prompt-review-sample/v1/level3` |

The same seed and row count always give the same positions, so adding override or approval rows later changes only the `reviewedBy` cell of a row, not which rows are in the sample. Unreviewed prompts ship, and the game says so on the Sources & licences screen.

## Known limitations

- The Lay to rest step needs a mouse, a finger or a pen to draw each stroke, so a keyboard-only player cannot lay a ghost to rest; that player can only give up.

## Usage

### Build the dataset

Prerequisites: Node and npm, and the raw datasets present under `data/raw/` (they ship in the repo).

```
npm run build:data
```

This reads the three character lists (`data/character-list.txt`, `data/character-list-level2.txt`, `data/character-list-level3.txt`), the raw datasets under `data/raw/`, and the prompt files described below, and writes three outputs, one per level:

| Level | Dataset | Review file |
| --- | --- | --- |
| 1 | `app/public/data/characters.json` | `data/prompt-review.csv` |
| 2 | `app/public/data/characters-level2.json` | `data/prompt-review-level2.csv` |
| 3 | `app/public/data/characters-level3.json` | `data/prompt-review-level3.csv` |

It also writes:

- `app/public/data/levels.json`, the level manifest: for each level its file, character count, average stroke count and three example meanings.
- `data/prompt-review-sample-level2.csv` and `data/prompt-review-sample-level3.csv`, the review samples, and `data/prompt-review-sample-provenance.json`, the sample provenance (see [Prompt review](#prompt-review)).
- `data/prompt-rule-changes.csv`, the prompts of levels 2 and 3 that differ from the original rule's choice (see [Clue rule for levels 2 and 3](#clue-rule-for-levels-2-and-3)).
- `app/src/data/promptCounts.generated.ts` and the block between the `prompt-counts` markers in this README.

If any level fails, the build reports the failures for all levels and writes none of these files. It runs fully offline — no network access, no API keys, no runtime LLM calls — and is deterministic: the same inputs always produce byte-for-byte identical output.

Prompt inputs written by the human, not by any script or by Kiro:

- `data/prompt-overrides.csv`: level 1 overrides by entry index.
- `data/prompt-overrides-level2.csv` and `data/prompt-overrides-level3.csv` (optional): overrides by entry index for levels 2 and 3, with the columns of `data/prompt-overrides.csv`. An absent file means no overrides.
- `data/prompt-approvals.csv` (optional): the header `character,reviewedBy`, one row for each level 2 or level 3 character whose prompt a human accepted unchanged.

In the level 2 and 3 files, `reviewedBy` must be exactly `human`; the build rejects any other value, and a character outside levels 2 and 3 in the approvals file. A character with an override row or an approval row gets `promptReview` `"reviewed"`; every other level 2 and level 3 character gets `"unreviewed"`. In a review file, `reviewedBy` is `human` for those rows and empty for the others.

### Check the layout width in a real browser

```
npm run test:e2e:install
npm run test:e2e
```

Run `npm run test:e2e:install` once; it downloads Chromium. `npm run test:e2e` then builds the app, serves it with `vite preview` on port 4173 under `/ghost-script/`, and runs five spec files: no-horizontal-overflow, fits-one-screen, summon-ink, first-meeting and screenshots. `e2e/no-horizontal-overflow.spec.ts` opens five screens at 375 and 320 px wide (Sources & licences, the Graveyard, How Cangjie works, the Summon step and the Write step) and checks that the page does not scroll sideways. `e2e/fits-one-screen.spec.ts` runs at 1024 × 768 and 375 × 812: it checks that the Summon step and the Write step fit in the viewport without vertical scrolling, that "Next ghost" is inside the viewport, and that the page scrolls back to the top on "Next ghost". The two specs that type keys read every letter from `characters.json` at test time.

`e2e/screenshots.spec.ts` also writes four PNGs at 1024 × 768 and at 375 × 812 (the intro, the Summon step after one key, the Write step, and the Graveyard with a seeded history) to `e2e/screenshots/`, named like `intro-1024x768.png`. The folder is gitignored and is rewritten on every run. The spec reads the key from `characters.json` and checks that no control or text lies inside the moon disc.

`npm test` does not run this check, and the deploy workflow does not run it either.

## Kiro tooling

Three Kiro-native tools sit around the character dataset. None of them changes the game or the shipped web app.

### Data check hook

The hook is defined in `.kiro/hooks/data-check-on-save.json`. It fires after a file save (`PostFileSave`) and watches these inputs:

- `data/character-list.txt`, `data/character-list-level2.txt` and `data/character-list-level3.txt`
- `data/prompt-overrides.csv`, `data/prompt-overrides-level2.csv` and `data/prompt-overrides-level3.csv`
- `data/prompt-approvals.csv`
- anything under `data/raw/`

When one of them is saved, the hook runs `npm run check:data --silent`. That command runs `npm run build:data`, then `npm run test:data` (`vitest run --project node`), and stops at the first step that fails. The `build:data` step writes all three outputs (the three level datasets, with the level manifest, the review files, the review samples and their provenance), so the check covers every level. The hook does not watch the generated files (the datasets, the review files and the rule-changes file), so a rebuild does not fire it again.

- On success, the first line printed is `DATA CHECK PASSED: build:data and test:data succeeded`.
- On failure, the first line is `DATA CHECK FAILED: <step>` (the name of the failing step), followed by the last 40 lines of that step's output.
- A bad override index in `data/prompt-overrides.csv` fails the build with a message that names the file and the column to fix. A negative index is rejected earlier, by the CSV parser, as a `malformed-row`.

Saving any watched input fires the hook once, whether a person or the Kiro agent saves it, as long as hooks are loaded. After the hook file is first added, a window reload may be needed before it loads.

Verified by hand: after a window reload, a person saved `data/prompt-overrides.csv` with a bad entry index on the 吧 row. The Kiro chat reported `DATA CHECK FAILED: build:data` with the entry-index message. Reverting the row and saving again reported `DATA CHECK PASSED`.

The Kiro IDE cannot create a manual-trigger hook, so to run the same check on demand, run this in a terminal from the repository root:

```
npm run check:data
```

### Accuracy reviewer

`.kiro/agents/accuracy-reviewer.json` defines a custom agent that checks the app text, specs and README against `content-accuracy.md`. Pick `accuracy-reviewer` in the Kiro agent picker and ask it to review. It is read-only: its only tool is `read`, and writing files and running shell commands are denied.

For each violation it reports one line, `path:line  [rule]  "quoted text"`. If it finds nothing, it reports `No findings` and lists the files it checked. It quotes the text and never proposes replacement character data.

### Cangjie Oracle (MCP server)

The Oracle is a small MCP server in the `oracle/` workspace. It uses `@modelcontextprotocol/sdk` over stdio and opens no network connection. Start it by hand with:

```
npm run oracle
```

Kiro starts it for you: it is registered as `cangjie-oracle` in `.kiro/settings/mcp.json` (command `npx --no-install tsx oracle/src/index.ts`). It offers three tools:

| Tool | Input | Returns |
| --- | --- | --- |
| `lookup` | `character` | the stored Cangjie code, its source (Unihan 18.0.0 `kCangjie`, which Unicode marks provisional), and whether the character is playable in the summon step |
| `verify` | `character`, `code` | whether the code matches the stored one. The code is converted to upper case, then must be 1 to 5 letters from A to Y; the result includes the normalised code |
| `decompose` | `character` | the IDS decomposition, the component list, the radical and the `atomic` flag, from Make Me a Hanzi data as stored in our dataset |

A character that is not in the dataset returns `found: false`; the Oracle does not guess. The registered workspace server reads only the three level datasets, `app/public/data/characters.json`, `characters-level2.json` and `characters-level3.json`, which together hold the 1,200 characters (the paths are resolved from the module, not from the working directory) and returns only values stored there, so it generates no character data. Those values keep the dataset's licences; see [Data and licences](#data-and-licences). The Power (next section) reads its own derived copy instead.

### Oracle Power

`oracle/power/` packages the Oracle as a Kiro Power: `plugin.json`, `mcp.json`, a skill at `skills/cangjie-oracle/SKILL.md`, a bundled server `server.mjs`, its own data copy `data/oracle-data.json`, `NOTICE.md` and a `licenses/` folder. To import it, open the Powers panel, choose Add Custom Power, then Import power from a folder, and select `oracle/power/`.

The Power is self-contained. Its `mcp.json` runs plain `node` on `${PLUGIN_ROOT}/server.mjs`, with `${PLUGIN_ROOT}` standing for the installed Power folder. The server needs no `npx`, no `tsx` and no `node_modules`, and reads only `oracle/power/data/oracle-data.json`, a derived copy of the 1,200 records, so it works from the Power folder alone. A human tested the import in Kiro on Nov 18, 2026, with the workspace `cangjie-oracle` server disabled. After re-importing `oracle/power`, a new chat was asked "Use the Cangjie oracle to look up 明". Kiro made two tool calls and answered: Cangjie code AB, source Unihan 18.0.0 field kCangjie (provisional), playable yes.

Regenerate the bundle and the data copy with `npm run build:power`. The generated files are committed, and `npm test` fails if they are stale.
